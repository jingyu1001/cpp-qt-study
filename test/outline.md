## 1. 课程定位与边界

### 1.1 定位

本教程是按**自学教程**设计的 Qt 6 项目式课程。学习者用 60 学时（45 小时）完成 Qt C++ 桌面开发的主干能力训练，并通过 23 种 GoF 设计模式的场景化教学与一个轻量 ECS 框架模块，建立“能写、能拆、能扩展、能交付”的工程能力。

课程结束后，学习者应能：

- 独立使用 Qt Widgets 与 Qt Quick/QML 开发可交付的桌面应用；
- 正确使用信号槽、事件、模型/视图、多线程、网络、数据库、串口、图表与多媒体等模块；
- 在真实场景中识别并落地 23 种设计模式，而不是背诵定义；
- 理解并实现一个最小 ECS（Entity-Component-System）框架，能将其与 Qt 的场景层对接；
- 用 CMake 组织工程、用 Git 迭代、用测试与部署工具完成交付。

60 学时是**引导学习时间**；单元练习、模块 demo、23 张模式卡与 4 个项目均为课外投入。项目预计合计 115–165 小时，不计入 60 学时。

### 1.2 边界（本课程不做什么）

- **不照搬参考书**：参考书只用于核对 Qt 语法与主题范围；教程正文必须按本大纲与 `deepseek.md` 独立编写。
- **不是 Qt 全量 API 手册**：只覆盖就业与生产中最常用的主干模块；冷门模块不展开。
- **不是游戏引擎课程**：ECS 模块是架构教学与轻量实现，不做完整渲染、物理或资源管线。
- **本阶段不做项目详细设计**：项目只保留概念层（背景、用户、需求、约束、验收概念），详细设计在对应阶段完成且用户明确指令后启动。
- **不把 23 种模式讲成孤立理论**：每个模式必须绑定 Qt 场景与可运行的小练习。
- **明确排除**：Qt 3D/Quick 3D、移动端与嵌入式交叉编译、Qt for Python、QML 高级渲染管线、服务端数据库与云平台、完整游戏引擎。

## 2. 学习目标

### 2.1 知识目标

- 掌握 Qt 6 的对象模型、元对象系统、信号槽、事件循环与内存管理；
- 掌握 Widgets 界面、布局、主窗口、对话框、模型/视图、绘图、图表、多媒体；
- 掌握 QML 语法、Qt Quick Controls、QML 与 C++ 的互操作；
- 掌握 QThread、TCP/UDP、SQLite、QSerialPort；能使用 QtConcurrent、HTTP/WebSocket；
- 了解国际化（tr()/QTranslator/lupdate）与日志（qDebug/QLoggingCategory）的基本用法；
- 理解 23 种 GoF 设计模式的意图、结构、适用场景与反例；
- 理解 ECS 的数据布局、组件存储、查询与系统调度。

### 2.2 能力目标

- 能从一个需求说明拆出界面、数据、并发、持久化与交付方案；
- 能在 Qt 项目中正确选型设计模式，避免过度设计；
- 能定位并修复常见的 Qt 崩溃、泄漏、卡顿、跨线程与网络问题；
- 能编写可读、可测、可部署的 CMake 工程；
- 能对教程内容与代码进行自审，并按审阅意见修订。

### 2.3 工程素养目标

- 命名、目录、提交、文档遵循 `deepseek.md`；
- 先设计后编码，先验证后提交；
- 对不确定的 API/版本行为查官方文档，不凭记忆下结论；
- 对项目范围与不做的事有明确边界意识。

## 4. 教学与写作约定

### 4.1 学习单元与时间预算

- 60 学时 = 30 个学习单元 × 90 分钟；不包含项目时间。
- 每个 90 分钟单元的建议结构：**目标与场景 5 分钟 + 知识讲解 35 分钟 + 模式切片 25 分钟 + 动手实践 20 分钟 + 小结与作业 5 分钟**。
- 课堂/引导时间只做“最小闭环”；完整练习、23 张模式卡与模块 demo 在课外完成。**此口径已由用户确认（2026-10-28）：60 学时只含讲解与引导实践，练习/demo 不计入。**
- 每个单元至少产出一个可检查的练习；**每个模块至少一个可运行 demo**，不要求 30 个独立 demo。
- 每个模块最后一次单元用于阶段验收（演示 + 设计自述 + 代码抽查），不另设“阶段测验”。验收单元的时间结构：**首讲 25 + 知识讲解/复盘 30 + 验收抽查 25 + 小结 10 = 90 分钟**；无首讲单元该时段并入复盘；模块 demo 在课外完成，验收时演示（可录屏）；复现内容改为课外整理模式矩阵、课内抽查。

### 4.2 设计模式教学法

每个模式按“五段式”教学，禁止只讲 UML 定义：

1. **场景**：一个真实的 Qt 开发痛点；
2. **问题**：不用该模式会怎么写、会坏在哪；
3. **结构**：角色、协作、关键约束；
4. **Qt 载体**：在 Qt 中的自然落点与最小示例；
5. **反例与边界**：什么时候不该用、常见误用。

**每个学习单元最多首讲 1 种新模式**；复现与预告必须在单元表中明确标注。每个模式配一张模式卡（意图、角色、Qt 场景、最小练习、反例、相关模式），模式卡在课外完成。

模式载体的角色必须在教程中写清：

- Singleton 以 qApp 为“全局访问点”示例时，注明它与 GoF 延迟初始化单例的差别；主体示例用配置服务。
- Bridge 的角色按 Qt 结构写：QPainter＝抽象、QPaintEngine＝实现者、QPaintDevice＝绘制表面。
- Flyweight 以组件数据/资源缓存为主载体；QString 隐式共享只作“相关机制”。
- Decorator 必须说明与 Strategy、Proxy 的边界；委托叠加要说明“装饰 base delegate”，另补 QIODevice 装饰示例。
- Visitor 注明 Qt 无内建 accept，需自建访问者。
- Proxy 必须讲清与 Decorator、Adapter 的边界。

### 4.3 命名与代码规范

遵循 `deepseek.md`：

- 变量：蛇形命名，如 `a_word_...`；
- 函数：小驼峰，如 `aWord...()`；
- 常量与宏：全大写蛇形，如 `A_WORD_...`；
- 类名、文件名、信号槽、成员变量前缀等未在 `deepseek.md` 规定的部分，由首篇教程统一约定并提交用户确认，不自行扩充规矩。

### 4.4 教程与代码的产出顺序

1. 教程正文给出完整、可运行的参考实现（含 CMake 工程）；
2. 学习者在 `demo/` 中独立复现，允许差异，但教程必须标注；
3. Review2 以教程为基准核对 `demo/` 与 `project/` 代码；
4. 教程片段与 `demo/` 代码不一致时，以教程为准并修正 demo；若教程有误，先改教程再改 demo。

## 8. ECS 框架模块

### 8.1 定位

ECS（Entity-Component-System）是本课程除 Qt 与设计模式外的第三个知识支柱，安排在模块 D（单元 20–22，共 6 学时）。

目标不是做游戏引擎，而是：

- 理解“数据与行为分离”对可扩展性与性能的意义；
- 用 C++17 从零实现一个**轻量、可测试**的 ECS 教学框架；
- 把 ECS 与 Qt 的 QGraphicsScene 对接；
- 用设计模式解释 ECS 内部结构（Flyweight、Prototype、Visitor），并辨析不适用模式。

教学方式：教程提供完整、可运行的 ECS 参考实现，学习者在之上改造与扩展；不是从空白文件开始手写全部细节。

### 8.2 范围与边界

| 包含 | 不包含 |
| --- | --- |
| Entity ID 与代际（generation） | 完整游戏引擎 |
| 组件注册与存储（稀疏集/连续存储概念） | 物理、动画、资源管线 |
| System 注册、查询与调度 | archetype 优化、多线程 Job 系统 |
| 事件/消息队列 | 网络同步与回滚 |
| 与 QGraphicsScene 的适配 | 自定义渲染器/着色器 |
| 序列化、场景导出与编辑器雏形 | 生产级 ECS 性能优化 |
| 单元测试与性能统计 | QML 适配（留到 P3 详细设计） |

默认**从零实现**，不引入 EnTT/flecs 等第三方 ECS 库；若用户明确要求改用现成库，可将单元 20–21 调整为“库集成 + 架构对照”，单元 22 的综合作品保持不变。

### 8.3 课时拆分

| 单元 | 主题 | 关键内容 | 产出 |

## 9. 项目体系（概念层）

### 9.1 项目原则

1. **独立设计**：4 个项目相互独立，不共享业务代码；各自独立 CMake 工程、独立目录、独立验收。
2. **只做概念层**：本大纲只定义背景、用户、需求、约束、交付物与验收概念；不写架构、类图、接口、数据库表、界面稿与代码。

4. **详细设计后置**：只有当对应阶段学习完成、概念评审通过，且用户明确指令“开始详细设计 Pn”时，才进入详细设计；此前不得提前展开。
5. **难度递进**：P1 → P4 难度递增，分别覆盖 Widgets/数据、可视化、QML+ECS、网络+设备+数据库。

- **背景**：办公与学习场景中，下载目录与资料目录长期堆积，重复文件多、命名混乱、检索困难。
- **目标用户**：普通办公人员、学生、需要整理大量本地资料的用户。
- **核心需求（概念级）**：

  - 按规则批量重命名（前缀/序号/日期/替换），支持预览与 dry-run；
  - 识别重复文件（判定策略待定）；
  - 按文件名与内容关键字搜索；
  - 操作前确认、操作日志与可回滚；

- **非功能需求**：大目录扫描采用分批遍历 + 事件循环驱动，界面保持可响应（不依赖多线程）；异常路径与长路径可处理；不误删、不覆盖；离线单机。
- **约束与不做**：不做云同步、不做系统级清理、不修改系统目录、不需要管理员权限。

### 9.5 P3：QML + ECS 场景编辑器

- **背景**：教学与原型阶段需要一个可视化的场景编辑工具，用 ECS 组织实体与组件，验证“数据驱动 + 系统更新”的架构。
- **目标用户**：学习 ECS 的开发者、需要快速搭建 2D 场景原型的教学/设计人员。
- **核心需求（概念级）**：
  - 创建/删除实体，挂载/移除组件（变换、渲染、行为等）；
  - 场景树与属性面板联动；
  - 系统启停与运行预览；
  - 场景保存/加载（格式待定）；
  - 撤销/重做；
  - 基础性能统计（实体数、帧时间）。
- **非功能需求**：千级实体可交互；60 FPS 目标；组件可扩展；异常数据不崩溃。
- **约束与不做**：不做完整游戏引擎、不做 3D、不做资源商店、不做多用户协作。
- **范围说明**：QML 与 ECS 的桥接不在模块 D 覆盖范围内，属 P3 详细设计需解决的问题。
- **交付物（概念阶段）**：需求说明、组件清单（概念级）、验收场景。
- **关联单元**：D1–D6（17–22）；重点 18/20/21/22。
- **详细设计启动条件**：模块 D 阶段验收通过 + 用户明确指令 + 概念文档通过 Review1。
- **验收概念**：创建含至少 3 类组件、3 个系统的场景，保存后重新加载一致，能撤销一次编辑并预览运行。

### 9.6 P4：网络化设备监控平台

- **背景**：实验室与小规模现场需要把分散设备（串口/TCP）的数据集中展示、报警与留存，现成方案成本高或不适配。
- **目标用户**：实验室管理员、小型工业现场运维人员、设备调试工程师。
- **核心需求（概念级）**：
  - 设备接入（串口/TCP），连接管理与断线重连；
  - 实时数据展示与曲线；
  - 阈值报警与报警记录；
  - 历史数据存储与查询（后端待定）；
  - 多客户端查看（局域网）；
  - 日志、导出与基础权限。
- **非功能需求**：长时间运行稳定；断线可恢复；数据不丢不乱序；UI 不被采集阻塞；日志可追溯。
- **约束与不做**：局域网部署、Windows 为主（具体环境待确认）；不做云平台、不做大规模集群、不做完整 SCADA。
- **交付物（概念阶段）**：需求说明、设备协议概念、验收场景、部署边界。
- **关联单元**：E1–E6（23–28），辅以 C3（15）；重点 23/25/27/28。
- **详细设计启动条件**：模块 E 阶段验收通过 + 用户明确指令 + 概念文档通过 Review1。
- **验收概念**：模拟设备接入后，实时曲线、报警、历史查询、断线重连均按验收场景通过。

## 10. 学习检查与产出

### 10.1 自检项

| 项目 | 建议权重（自评） | 说明 |
| --- | --- | --- |
| 单元练习与模块 demo | 30% | 每个模块至少 1 个可运行 demo；其余练习课后完成 |

### 10.2 阶段验收

每个模块结束时进行一次阶段验收，形式为“演示 + 设计自述 + 代码抽查”：

- 演示：运行本模块 demo，展示关键路径；
- 设计自述：解释设计取舍、模式落点、失败场景；
- 代码抽查：命名、资源管理、线程安全、异常处理；
- 测试要求：模块 C 起，每个模块至少 1 个 Qt Test 用例；A/B 模块用自检清单与手动验证，F 模块系统补齐；
- 执行方式：自学环境下由学习者自检，留存演示录屏、设计自述与测试日志，Review1 抽查。

### 10.3 结课标准

- 完成 30 个学习单元的练习；
- 6 个模块各有一个可运行 demo；
- 23 张模式卡齐全，能通过随机抽问；
- 4 个项目概念文档通过评审；
- 能独立完成一次“配置 → 构建 → 测试 → 打包”的交付流程。

项目实现部分的检查在详细设计启动后另行约定，不计入 60 学时。

## 11. 教程编写与审阅流程

### 11.1 大纲的效力

- 本大纲是教程正文的唯一结构依据；教程不得擅自增删单元、调整学时或改变项目边界。
- 需要调整大纲时，由用户确认后修订版本号，并重新走 Review1 审阅；不得在正文中“顺手”扩展大纲。

### 11.2 单篇教程的编写流程

1. 从大纲取一个学习单元（或一组紧密单元），确认前置单元已完成；
2. 阅读 `deepseek.md` 与相关单元条目，列出本单元目标、知识点、模式切片、实践产出；
3. 独立编写教程正文，不凭记忆复述参考书；
4. 自检：技术断言有依据、代码与 `demo/` 一致、命名合规、无超纲内容；
5. 提交 Review1 审阅（内容与规范）；
6. 按审阅意见修订，复审通过后入库 `test/`；
7. 提交 Git，提交信息按约定格式。

### 11.3 双审阅机制

- **Review1（内容审阅）**：审教程与大纲、`deepseek.md` 的一致性，技术准确性，结构完整性，前后篇自洽；只读，不改稿。
- **Review2（代码审阅）**：审用户编写的 `demo/`、`project/` 代码，覆盖命名、拼写、实现一致性、隐藏 bug、Qt/C++/CMake 问题；只读，不改代码。
- 审阅结论按“阻断 / 重要 / 建议”分级，由 Lead 汇总、用户决策；未通过的教程不得入库。
- 审阅角色属于协作流程，不是学习目标；学习者只需按审阅意见修订。

### 11.4 变更与版本

- 大纲版本：`v0.x` 草案、`v1.0` 审阅通过；
- 每次大纲修订记录变更摘要与原因；
- 教程正文与大纲版本对应，避免“新大纲配旧教程”。
